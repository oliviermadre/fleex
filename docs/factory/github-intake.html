GitHub entre par l'usine

Chaque notification GitHub qui te concerne (participating) devient un item, un par sujet (issue, PR). L'intake agrège une rafale sur le quai, commente le ticket Fleex lié s'il existe, et quand un sujet déjà avancé sur le plancher reçoit du nouveau, pose une seule question à un LLM : est-ce que ça aurait pu changer l'outcome de ce qui a déjà été fait ? Choix · ce que l'intake affiche

Les resets et ce qui est ignoré se passent dans l'intake, hors du plancher. Faut-il les compter sur le quai ? (Le choix change le dessin du quai ci-dessus.)

Le check, en une question

Update check · what the model is asked

New activity came on a subject whose item has already moved on the floor. Would it have been able to change the outcome of what was done on the item so far?

yes: it brings new information, or invalidates what the work rested on → the item is reset
new: it is about something else on the same subject → a new item
no: nothing useful (thanks, a reaction) → ignored

It is given

  • item its comments, its tags, where it is
  • stations what each one it went through answered, and what the current one is doing
  • new the comments of the burst, gathered over the quiet delay

It answers

{ "verdict": "yes" | "new" | "no", "reason": "the colour changed from red to aubergine: Spec, Dev and QA worked on red" }
  • Pas de LLM quand c'est évident : l'item attend encore sur le quai (on agrège), ou un ticket est lié (commentaire sur le ticket).
  • Oui = reset, toujours, même si l'item attend sur une question : en QA, un contexte qui aurait pu changer la spec impose de rejouer toute la lane. Le run en cours est arrêté ; l'item revient au quai avec tous ses commentaires et refait sa lane. Ce que les stations avaient dit reste dans son historique, et son brief dit pourquoi il a été remis à zéro.
  • Un item archivé suit la même question : oui, il revient au quai ; nouveau, un nouvel item ; non, rien.
  • Si le check échoue (quota, erreur) : un nouvel item relié, signalé. Rien de perdu, rien d'interrompu.
  • Le coût : un run court par rafale, sur un modèle bon marché, compté dans les limites du Factory. Le check se coupe sur l'intake ; sans lui, c'est toujours un nouvel item relié.
  • Gmail ne change pas : pas de check, un mail reste une conversation qui revient.

Ce que l'intake pose sur chaque item, en tags (lus par les bras) et en champs :

reason:review_requested · repo:evaneos/shop · kind:pr · state:open · draft:no · bot:no

Et selon le cas : linked:yes + le ticket (#812) ; follow-up:yes + l'item qu'il suit (un sujet nouveau sur la même PR) ; reset:1 et la raison, après un reset.

La clé d'un item GitHub est le sujet plus son numéro d'ordre (evaneos/shop#355·2) : un sujet nouveau sur la même PR donne un deuxième item, relié. Le sujet seul sert à trouver le ticket lié et les items déjà là.

Le commentaire sur le ticket lié cite les commentaires de la rafale en entier, auteur et heure.
