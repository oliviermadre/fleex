The shift

The session is ephemeral compute.
The ticket is durable work.

The current generation of agent environments won the parallelization battle — isolated worktrees, many sessions at once. Then the session ends, and everything it knew evaporates.

Session-first (the current ADEs)

  • The session grid is the main screen.
  • Tickets are imported as prompts from Linear or Jira.
  • One worktree = one task = one repo.
  • When a session closes, its context becomes a transcript nobody rereads.
  • Costs live in your provider dashboard, unattributed.

Ticket-first (Fleex)

  • The kanban is the main screen. Sessions are the debug view.
  • The ticket is the persistent primitive — it owns the workspace, sessions, deliverables and costs.
  • One ticket = one workspace = N repos × N worktrees × N PRs.
  • Every session — even a manual terminal one — leaves a summary in the ticket.
  • Every dollar is attributed to a ticket, a persona, a panel.

Sessions come and go. The ticket accumulates. // That's the whole idea.

Six primitives. One system.

Each one is useful alone. Wired together through the ticket, they compound.

Ticket-first kanban

A local-first board (SQLite, PostgreSQL, Supabase or JSON) that is your orchestrator, not a mirror of one. Drag a ticket — work starts.

One workspace per ticket

Real tasks cross repo boundaries. A Fleex ticket natively holds multiple repos, worktrees and PRs — front + back + infra is one ticket, not three orphaned sessions.

Start where you are

You don't have to believe in stage 3 to start at stage 1.

Most of us climbed this ladder one rung at a time. Fleex is useful from the first rung — and it's already holding the next one when you reach for it.

Stage 0

One session at a time

You talk to one agent in one terminal. Fleex already saves a summary when it ends.

Stage 1

Parallel sessions

Isolated worktrees, live terminals side by side. Everything a session manager gives you — start here.

Stage 2

Project management

More parallelism → you need to track who's doing what. Group sessions into tickets on the kanban.

Stage 3

Knowledge & control

Tickets accumulate context, deliverables and costs. Your delivery has a memory — and a ledger.

The honest part: you won't feel the need for stages 2–3 until you've lived stage 1. That's fine. Fleex meets you at the session grid and grows with you.

For the builders

“I could build that myself.”
Yes. You could.

Every feature below is replicable with a script — we know, we wrote those scripts first. The value isn't any single piece. It's that they're already wired to each other, through the ticket.

I can save context with a git or Claude hook
✓ true — about 30 lines

Now make it fire for SDK sessions and manual terminal ones, land in the right ticket, sit next to the deliverables it explains, and export with everything else. In Fleex that hook ships wired. Zero config.

I can track costs with ccusage
✓ true — great tool

It tells you what you spent. It can't tell you what ticket FLX-142 cost, across four sessions, two personas and a panel — because it doesn't know tickets exist. Attribution needs the primitive.

I can do multi-repo with /add-files
✓ true — for one session

That's files in a context window, not work across repos. A Fleex ticket holds two worktrees and two PRs with their reviews, discussion and history — and it's still one object on your board next week.

Fleex is those scripts — already written, already wired to the ticket, already exporting to a format you own.

Install

One command. An interactive wizard does the rest.

Today Fleex installs from the terminal — fitting, for the last time you'll need to live there.

bash
# install — clones to ~/.fleex, checks prerequisites, runs the setup wizard

$ curl -fsSL https://raw.githubusercontent.com/oliviermadre/fleex/main/install.sh | bash

# then start everything — gateway, server, web UI
$ fleex start
# → opens your browser. Add a repo, spin up agents, go.
requires: git bun ≥ 1.3.5 tmux claude CLI gh (optional)

The wizard sets you up

Display name, worktree path, storage driver (SQLite by default — nothing to host). It seeds three agent personas and a personal board so the app isn't empty on first launch.

Your first ten minutes

You don't need to change how you work. Start with parallel sessions — the thing you came for — and let the ticket reveal itself.

Install & start

Run the install command, answer the wizard, then fleex start. Your browser opens on a board that already has personas and a demo ticket to explore.

→ first screen in ~3 minutes

Add a repo, launch parallel sessions

Register a repository, open two or three sessions in isolated worktrees, watch the terminals stream live. Familiar territory — this is the session-manager part.

→ everything your current tool does

Group them into a ticket

Those three sessions are really one piece of work. Promote them into a ticket: it now owns the worktrees, the PRs, and the conversation. Drag it across the board as it progresses.

→ the work has a name and a place

End a session. Watch the summary land.

Close any session — even a plain terminal one. A summary appears in the ticket automatically: what was done, what was decided, what's left. No hook to write. It was always on.

→ this is the aha. Nothing evaporates.

From here, the ladder is yours: @mention a reviewer persona, convene a panel, check what the ticket cost, export it all to OKF. Or don't — stage 1 alone is already a good tool.
